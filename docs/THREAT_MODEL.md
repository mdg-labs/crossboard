# Crossboard — Threat Model

Crossboard is a self-hosted web app (one Node.js process, one SQLite file, one container) that shows the open GitHub issues of every repository a signed-in user reaches through the instance's own GitHub App. It is read-only against GitHub. Users sign in with GitHub; the instance restricts who may sign in and which GitHub App installations it syncs through an allowlist of GitHub logins and organizations. One instance may serve several users, and a hosted multi-tenant version may follow, so nothing may assume a single user.

This file follows the threat-model format of the security-audit skill (decision D-17 in `docs/SPEC.md`). Sections 1–6 are pasted verbatim into audit agents and are written to stand on their own; section 7 is for maintainers.

## 1. Assets

What an attacker wants, from most to least valuable. Every finding's impact must name one of these.

- **A1 GitHub App credentials.** The App's private key (signs short-lived installation tokens), its OAuth client secret and its webhook secret. Stored encrypted in the database when created through first-run setup, or supplied as environment variables. With the private key an attacker can mint installation tokens and read every issue of every installation of the App, for every user, without signing in.
- **A2 `CROSSBOARD_APP_SECRET`.** The key material from which the encryption key for all secrets at rest is derived. With it, a copy of the database file yields every stored token and credential (A1, A3). It also keys the HMAC that signs the setup cookie.
- **A3 User tokens and installation tokens.** Each signed-in user has a GitHub user access token (8 h) and refresh token (6 months), stored encrypted. Installation access tokens (1 h) are minted from the private key and held in memory. A user token grants that user's GitHub identity and the list of repositories they reach; an installation token grants read access to the issues of every repository of one installation.
- **A4 Private-repository issue data.** Titles, labels, assignees, milestones, parent and dependency links, bodies and comments of issues in private repositories, stored once per repository and shown only to users who have access to that repository on GitHub. Confidentiality across users and to non-users is the central property of the product. Public-repository issue data has the same integrity needs but lower confidentiality value.
- **A5 Boards and saved views.** Each user's own boards, columns and saved filters. They are strictly personal: other users, including other allowed users of the same instance, must not read, change or delete them. Their loss is irreversible because they exist only in Crossboard's database.
- **A6 Sessions.** The session cookie and the server-side session row. Possession of a live session is possession of that user's view of the product for up to 30 days of inactivity.
- **A7 The setup capability.** Until a GitHub App exists, whoever completes first-run setup chooses which GitHub App the instance trusts and therefore owns the instance. The setup token and the setup cookie are the proof.
- **A8 The user's browser.** Script execution in the Crossboard origin acts as the signed-in user against every API route and can read everything that user can see. Content from GitHub issue authors is rendered there.
- **A9 The host and availability.** The container, the data volume, the process's ability to serve, and the CI runner that builds and publishes the image. Availability covers the instance staying up and keeping within GitHub's rate limits (a flood or a crafted request that exhausts an installation's hourly budget or the process's memory denies service to every user).
- **A10 The integrity of GitHub data.** Crossboard must never change anything on GitHub. A defect that lets any input cause a write to a user's repositories or organizations harms assets Crossboard does not even own.

## 2. Attackers

### 2.1 Anonymous internet client

Anyone who can reach the instance's HTTP port. **Can:** send arbitrary requests to every route, including the health, sign-in, setup and webhook routes; send malformed, oversized or very frequent requests; set arbitrary headers including `Origin` and `Content-Type`; run a web page in their own browser that makes cross-site requests to the instance on behalf of a visitor. **Cannot:** read any data or call any session-protected route without a session; hold the webhook secret, the setup token or any key; read the server's logs or database.

### 2.2 GitHub user who is not allow-listed

Any person with a GitHub account that is neither in the instance's allowed-user list nor a member of an allowed organization. Because the instance's GitHub App is public, this attacker **can**: complete the GitHub sign-in flow and be redirected back to the instance with a valid authorization code; install the public App on their own account or organizations, which makes GitHub send the instance `installation` webhooks (signed) and creates installations the instance has not approved; own repositories on which they can plant issue content. **Cannot:** obtain a session, a stored token or a user row on the instance; make the instance sync their installation's data or read data of any other installation; produce a webhook that passes signature verification (only GitHub, for this App, can).

### 2.3 Signed-in allowed user

A legitimate user of the instance acting beyond their rights. **Can:** call every session-protected route with arbitrary parameters; enumerate numeric board, view and issue identifiers and owner/repo/number path segments; submit crafted filter queries, board imports and saved views; hold sessions on several devices; lose access to a repository or organization on GitHub while their session stays alive. **Cannot:** read repositories, issues, boards or saved views that belong to another user or that their own GitHub access does not reach; see another user's tokens or sessions; reach the setup routes after setup is closed. **Goal:** read another user's data, repositories the user lacks access to, or act as another user (including through a CSRF-style cross-site request from a page they host).

### 2.4 Forged webhook sender

Anyone on the internet who knows the webhook URL and posts to it. **Can:** send arbitrary bodies and headers to the webhook route, replay a captured genuine delivery, send deliveries for installations that are not active, and send very large or very frequent requests. **Cannot:** produce a valid HMAC signature without the webhook secret. **Goal:** make the instance accept a payload that changes stored issues, purges a repository or installation, triggers refetches that burn an installation's rate-limit budget, or discloses information through error behavior.

### 2.5 Malicious issue author on a synced repository

Someone who can write issue titles, bodies, comments, labels and milestone names on a repository that the instance syncs (for example a stranger commenting on a public repository, or a contributor to a private one). **Can:** put arbitrary Markdown and HTML into issue bodies and comments (GitHub renders it to HTML, which the instance receives), pick label and milestone names containing quotes, markup or very long text, create very large issues and dependency or sub-issue graphs including cycles and self-references, and reference issues in other repositories. **Cannot:** sign in, call any Crossboard route, or make GitHub return HTML GitHub itself would not render. **Goal:** execute script in a Crossboard user's browser, inject markup or styles, load attacker-chosen resources, redirect a user, or corrupt or crash the instance through crafted fields.

### 2.6 Outside contributor and supply chain

A person who can open pull requests or issues against the Crossboard source repository once it is public, or the author of a third-party package or GitHub Action the build depends on. **Can:** propose changes that run in CI, publish a malicious version of a dependency, and craft pull request titles, branch names and file names that are interpolated into workflow steps. **Cannot:** merge, push to protected branches, or read repository secrets unless a workflow exposes them to untrusted code. **Goal:** run code on the CI runner, steal publish credentials, or ship a backdoored image.

### 2.7 The operator (trust ceiling)

The person who deploys and runs the instance. **Can by design:** read and set every environment variable including `CROSSBOARD_APP_SECRET` and the GitHub App credentials; read and change the database file and the data volume; read logs; edit the allowlists; delete stored credentials to re-run setup; run any code on the host and replace the image; read the setup token file in the data directory. Everything this attacker can do with those powers is **by design and never a finding**. Their mistakes are also out of scope (an `http://` public URL, a weak `CROSSBOARD_APP_SECRET` that still satisfies the length check, exposing the data volume). A defect is only in scope if it lets a lower attacker obtain operator powers, or if the product leaks operator-held secrets to a lower attacker.

GitHub itself is trusted to authenticate users, sign webhooks and answer API calls truthfully. Its _content_ (issue text, rendered HTML, names) is written by 2.5 and is not trusted.

## 3. Entry points, mapped to code

Every place outside input arrives. Paths are the repository layout the project is built to: the server lives under `apps/server/src/`, the SPA under `apps/web/src/`, the filter engine under `packages/query/`. Some of these paths may not exist yet while the first milestones are being built; a path listed here is where the entry point must live, and an entry point found anywhere else is itself a finding.

- **Process start and configuration.** Environment variables are read and validated only in `apps/server/src/config/`; process entry, migration run and HTTP listener in `apps/server/src/index.ts`; route wiring, global middleware (CSRF, security headers, static SPA serving, health) in `apps/server/src/app.ts`. The listener is a single port (default 3000).
- **First-run setup.** Pages and routes `GET /setup`, `POST /api/setup/token`, `POST /api/setup/manifest`, `GET /setup/callback`. Exist only while no GitHub App credentials are configured. Inputs: the setup token, the setup cookie, the account name to own the App, the `code` and `state` returned by GitHub, and the manifest-conversion response (which carries the private key, client secret and webhook secret). Code: `apps/server/src/auth/` (setup and manifest flow), `apps/server/src/security/` (token hashing, cookie signing, encryption).
- **Sign-in and sessions.** `GET /auth/login`, `GET /auth/callback`, `POST /auth/logout`; the `crossboard_session` cookie; the `return` path parameter that selects where a user lands after sign-in. Inputs: OAuth `code` and `state`, the state cookie, the session cookie, the `return` parameter, GitHub's answers about the user and their installations. Code: `apps/server/src/auth/`, allowlist decision in `apps/server/src/access/`.
- **Session-protected JSON API.** All `/api/*` routes except the health and setup routes: issues list and detail, lazy details, suggestions, saved views, boards (CRUD, cards, export, import), the current user, sync status and refresh. Inputs: query strings (`q` filter text, `sort`, `offset`, `limit`, `field`, `prefix`), path segments (`owner`, `repo`, `number`, board and view ids), JSON bodies (boards, views, a board import of up to 256 KB), the session cookie, `Origin` and `Content-Type` headers. Code: `apps/server/src/api/`, `apps/server/src/issues/`, `apps/server/src/boards/`, scoping helpers in `apps/server/src/access/`, filter parsing in `packages/query/`, request validation schemas in `apps/server/src/api/`.
- **Health endpoint.** `GET /api/health`, unauthenticated, returns status and version only. Code: `apps/server/src/app.ts`.
- **Webhook intake.** `POST /webhooks/github`. Inputs: raw body, `X-Hub-Signature-256`, `X-GitHub-Event`, `X-GitHub-Delivery`. Code: route and event handlers in `apps/server/src/webhooks/`, verification helpers in `apps/server/src/security/`, resulting work through `apps/server/src/jobs/` and `apps/server/src/sync/`.
- **Outbound GitHub client.** The single rate-limit-aware client for every REST and GraphQL call, token cache and ETag cache. Inputs: installation and user tokens, response bodies and headers from GitHub (issue data, rendered HTML, rate-limit headers, `retry-after`). Code: `apps/server/src/github/`, consumers in `apps/server/src/sync/`. Outbound hosts come from configuration; the two override variables for the GitHub API and web URLs exist for tests against a fake GitHub only.
- **Rendered HTML path.** GitHub's rendered `bodyHTML` for issue bodies and comments is sanitized on the server before storage and delivery (`apps/server/src/security/`, called from the detail fetch in `apps/server/src/sync/` and `apps/server/src/api/`); the SPA renders only that sanitized output, inside one dedicated container component, in `apps/web/src/` (detail panel and route `/i/:owner/:repo/:number`). The SPA injects no HTML other than those sanitized bodies; every other issue field it shows (titles, label and milestone names, logins) reaches the DOM as text.
- **Response headers and CSP.** Content-Security-Policy and other security headers are set by `apps/server/src/security/` and applied in `apps/server/src/app.ts`; the SPA's style and script delivery is configured in `apps/web/` (Vite build, the component library's CSP provider, `apps/web/index.html`).
- **Database and migrations.** SQLite file under the configured data directory, schema in `apps/server/src/db/schema/`, generated migrations in `apps/server/src/db/migrations/`, applied automatically at startup from `apps/server/src/index.ts`. Inputs: the existing database contents at upgrade time.
- **Background jobs.** The in-process queue and scheduler (`apps/server/src/jobs/`) run sync, reconciliation, session cleanup and access recomputation; their inputs are the database and GitHub's responses.
- **Browser storage.** The SPA keeps only per-viewer conveniences (board card expansion state) in `localStorage` in `apps/web/src/`; no secret or token may be stored there.
- **Container and packaging.** `Dockerfile`, `docker-compose.yml` and `.dockerignore` at the repository root: image contents, user, exposed port, volume, healthcheck.
- **CI and release workflows.** `.github/workflows/` (CI on pushes and pull requests, and the release workflow that builds and publishes the image on a version tag), running on a self-hosted runner; `scripts/` for helpers they call. Inputs: pull request metadata and code from forks, dependency versions, action versions, repository secrets and the registry credential.
- **Dependencies.** `package.json`, `pnpm-lock.yaml` and `pnpm-workspace.yaml` at the root and in each package; third-party code that runs in the server and in the browser.

## 4. Security invariants

Each invariant must hold on every code path that touches the named subject. A violation is a finding. Numbers are never reused or renumbered; a retired invariant keeps its number and is marked retired.

- **T1 Cross-user isolation.** Every API query that returns issue, repository, label, assignee, dependency, board, column or saved-view data is scoped by the session user. Issue data is stored once per repository and is returned only for repositories present in that user's computed access set; there is no code path that selects issues "across the whole database" for a request. A board or saved view is readable and writable only by its owner, and another user's identifier answers `404`. A lazy detail fetch for an issue happens only after the session user's access to its repository has been checked. For each changed route or query a test proves that a second user cannot see a repository, issue, board or saved view they lack access to.
- **T2 Tokens and credentials.** User access tokens, refresh tokens, the App private key, client secret and webhook secret are encrypted at rest with AES-256-GCM using a fresh random IV per value and a key derived from `CROSSBOARD_APP_SECRET`; no other secret-bearing column is stored in clear. A user access token with less than five minutes of life is refreshed before it is used; a failed refresh, or a revocation notice from GitHub for that user, deletes the user's tokens and sessions. Tokens and App credentials are never returned to the browser, never placed in a URL or a response body, and never written to logs or error messages (including configuration errors, which name a variable and never its value).
- **T3 Allowlist.** Sign-in and syncing stay restricted to allowed users and active installations. A GitHub account that is not allowed gets no session, no stored token and no user row, and the check happens before anything is stored. An installation whose account is not allow-listed and that no allowed user reaches is recorded but not synced, its repositories are never fetched, and its webhooks are acknowledged and dropped. The server refuses to start when no allowlist entry exists. Allowlist matching is case-insensitive and exact (no prefix or substring match).
- **T4 Webhook authentication.** `X-Hub-Signature-256` is verified over the raw body with a constant-time comparison against the webhook secret before the body is parsed, logged or acted on. A missing, malformed or wrong signature is rejected with `401` and no side effect (no database write, no job, no outbound call). Payload fields do not change stored issue fields directly except for removals; every other relevant event triggers a refetch from GitHub. Deliveries for inactive installations are dropped. Webhook payload bodies are not logged for private repositories at any level.
- **T5 HTML sanitizing.** Every path that sends GitHub-rendered HTML to the browser passes through the server-side sanitizer with its fixed allowlist: scripts, styles, iframes, forms, event-handler attributes and `style` attributes are removed; `href` accepts only `http`, `https` and `mailto`; `img` `src` accepts only `https`; links get `rel="noopener noreferrer nofollow"`; `class` is limited to the documented GitHub markdown prefixes. Sanitizing happens before storage and before delivery. The SPA never renders HTML that did not come through that path, never uses raw-HTML injection for any other field, and treats every other GitHub-supplied string as text. A test with a script and an `on*`-attribute payload proves it is stripped.
- **T6 Sessions and cookies.** The session cookie is HTTP-only, `SameSite=Lax` and `Secure` (except on `http://localhost`), holds a random 32-byte token, and only its SHA-256 hash is stored. Sessions expire after 30 days of inactivity; sign-out deletes the session; expired sessions are removed daily. The OAuth `state` is random, stored in a short-lived HTTP-only cookie and verified on callback. The post-sign-in `return` target is honoured only when it is a same-origin relative path.
- **T7 CSRF.** Every state-changing route (`POST`, `PATCH`, `DELETE`) rejects a missing or foreign `Origin` header (compared against the configured public URL) and any body that is not JSON. The only exemptions are the webhook route, authenticated by its signature, and the redirect-style `GET` callbacks of sign-in and setup, which are authenticated by their `state`. No `GET` route other than those two callbacks changes state.
- **T8 Migrations.** Migrations are generated, not hand-edited after commit, and apply cleanly on an existing database that already contains data, not only on an empty one. They never drop or rewrite user-created data (boards, columns, saved views) and never decrypt, re-encrypt or log secrets. Sync, purge and cleanup jobs never delete boards or saved views.
- **T9 No GitHub writes.** The server never sends a GraphQL mutation and never makes a REST call that changes GitHub data. The only non-`GET` calls are GraphQL queries and the credential exchanges: installation access tokens, the App-manifest conversion, and the OAuth code exchange and token refresh. The App requests only Issues: read and Metadata: read. All GitHub traffic goes through the one central client; no other module calls the GitHub libraries or `fetch` for GitHub directly.
- **T10 Setup token and setup lifecycle.** While no App credentials exist, the server generates a fresh random setup token at each start, stores only its hash, and serves only the setup flow (every other route redirects to it; the health route stays available). The submitted token is checked against its stored hash, a correct token yields a setup cookie that expires after 30 minutes, is HTTP-only and is signed with a key derived from `CROSSBOARD_APP_SECRET`; every later setup route requires that cookie. The manifest `state` is random, stored in the setup cookie, and a missing or mismatched `state` on the callback is rejected before the code is exchanged. Once credentials are stored (or all credential environment variables are set) the setup routes answer `404`; a partial set of credential variables is a startup error. The setup token is written at startup to a `0600` file in the data directory, which is removed when setup completes or when a start finds credentials; it is never logged and never appears in any response.
- **T11 Content-Security-Policy stays free of inline styles and scripts.** The policy sent with every HTML response uses `script-src 'self'` and `style-src 'self'` with no `unsafe-inline`, no `unsafe-eval`, no nonce or hash exceptions, `frame-ancestors 'none'`, `base-uri 'none'`, `connect-src 'self'`, and `form-action` limited to the instance and `https://github.com`. The SPA ships all CSS and JavaScript as same-origin files; the UI component library's inline `<style>` generation is disabled so no component needs an inline style element, and no code adds inline `<script>`, inline event handlers or `style` attributes that depend on a relaxed policy. Fonts and icons are bundled, never loaded from a CDN; image sources are limited to the instance, GitHub avatar and content hosts, and `data:`.
- **T12 Request validation and bounded input.** Every route validates query strings, path segments and bodies with a schema before use; `limit`, import size (256 KB), filter nesting depth, board and column counts and name lengths are bounded; database access uses the ORM's parameterized API, never string-built SQL. Error responses carry a code and a message and never a token or secret.
- **T13 Outbound requests only to GitHub.** The server's outbound HTTP requests go only to the configured GitHub API and web hosts (github.com by default); no request URL is built from issue content, webhook payloads or user input beyond validated owner, repository and number segments and GitHub-supplied node identifiers.
- **T14 No secrets in logs, repository or image.** Logs never contain tokens, secrets, cookies, the setup token (the startup warning names the file that holds it, not the token) or webhook bodies for private repositories. No credential, key or token-shaped example string is committed, baked into the image or printed by CI.
- **T15 Publishing is gated.** The container image is published only by the release workflow on a pushed version tag and by the nightly workflow on a push to `main`; no workflow triggered by a pull request holds publish credentials.
- **T16 Pull-request CI runs untrusted code with nothing to steal.** No workflow uses `pull_request_target` or `workflow_run` to reach pull-request code. Every workflow that runs on `pull_request` declares `permissions: contents: read` and nothing wider, receives no repository or environment secrets, checks out with `persist-credentials: false`, and references every third-party action by full commit SHA. No workflow step interpolates pull-request titles, branch names, file names or other contributor-controlled text into a shell command. How fork pull requests reach the self-hosted runner (isolation of the runner, its Docker daemon and its build cache) is not yet decided and is tracked in #67; until then they are kept off it by repository settings.

## 5. Accepted residuals

Risks accepted on purpose. A report that only restates one of these is not a finding.

- **R1 The operator can do everything.** The operator holds the encryption secret, the App credentials, the database and the host. Compromise or abuse at that level is out of scope. Reason: a self-hosted tool cannot defend its data against the person who runs it.
- **R2 Changing `CROSSBOARD_APP_SECRET` invalidates stored data.** There is no key rotation; a changed secret makes stored tokens and stored setup credentials unreadable, so users sign in again and setup is redone unless credentials come from the environment. Reason: rotation is deferred; failing closed is acceptable.
- **R3 The encryption key is derived from a single static secret.** Anyone holding both the database file and the secret reads all secrets. Reason: this is the intended trust boundary between host and data; the secret lives in the environment, not on the volume.
- **R4 A user keeps the last computed access for up to 60 minutes.** A user who loses access to a repository on GitHub can keep seeing already-synced issues of it until the periodic recomputation, a relevant webhook, or the next sign-in removes the access row. Reason: access is recomputed on a schedule and on events instead of on every request, to stay inside GitHub rate limits.
- **R5 Stored issue data can be briefly stale or, after a missed event, wrong.** A missed webhook leaves old data until reconciliation (15 minutes, or 2 without webhooks) or the daily resync fixes it. Reason: freshness is a rate-limit trade-off, not a confidentiality property.
- **R6 Installation records of non-allowed accounts are stored.** The instance records the id, account and creation time of any installation of its public App, even when that account is not allow-listed. Reason: needed to evaluate activity later; no issue data is fetched for them.
- **R7 Plain-HTTP deployments are possible.** Cookies are not `Secure` on `http://localhost`, and an operator may run behind a proxy that terminates TLS or serve over plain HTTP elsewhere. Reason: local use must work; transport security is the operator's responsibility.
- **R8 No rate limiting of sign-in, API or webhook requests by the application.** Abuse of the endpoints is bounded by their authentication, request limits and the reverse proxy, not by an in-app limiter. The one in-app limit is a once-per-60-seconds manual refresh per user, kept in memory and reset on restart. Reason: v1 targets one person or a small team; flooding is an operator and proxy concern.
- **R9 Sanitized GitHub HTML can still link or load images from the web.** Allowed `https` images and `http`/`https` links can leak a viewer's IP address and timing to the host an issue author chose. Reason: GitHub's own rendering behaves the same way; the CSP limits image hosts to GitHub's content domains.
- **R10 Memory and session state are per process.** Budget counters, the refresh limiter and queued jobs are in memory and lost on restart; there is no horizontal scaling. Reason: one-process design for v1.
- **R11 Private-repository image URLs in cached HTML expire.** Cached detail HTML is refetched after ten minutes for this reason; a stale image may break. Reason: GitHub-side behavior.
- **R12 A replayed genuine webhook delivery is processed again.** Deliveries are not deduplicated by `X-GitHub-Delivery`, so a captured delivery with a valid signature passes T4 when sent again. Its effect is that of the original event applied a second time: a refetch (debounced and deduplicated per issue, SPEC §6.2), or an old removal or purge that leaves the issue or repository missing until it is synced again from GitHub. Reason: capturing a delivery needs the TLS path between GitHub and the instance, which is the operator's (2.7) or a plain-HTTP deployment (R7); GitHub's own redelivery is available only to the App owner, who is the operator.

## 6. Severity rubric

Severity is decided by outcome and by the weakest attacker who can reach it. Name the asset (section 1) and the attacker (section 2) in every finding.

- **Critical.** An attacker without the operator's powers (2.1, 2.2, 2.4, 2.5 or 2.6) obtains any of: App credentials or the encryption secret (A1, A2); another user's tokens (A3); remote code execution on the host or the CI runner (A9); the ability to take over an uninitialised instance through setup (A7); or read access to private-repository issue data without a session or without access (A4); or any change to GitHub data (A10). No user interaction beyond normal use.
- **High.** An attacker obtains a significant part of the same outcomes with a precondition, for example: a signed-in allowed user (2.3) reads another user's or an inaccessible repository's issues, boards or saved views (A4, A5), or acts as another user (A6); script execution in a user's browser from issue content or a stored value (A8); a forged webhook is accepted and changes stored data or purges a repository; a non-allow-listed account obtains a session or a stored token (A3, A6); a state-changing route can be driven cross-site (CSRF) (A5, A6); a secret appears in logs, responses or the image (A1–A3); a destructive migration drops user-created boards or views (A5); a CI weakness lets a pull request from a fork reach secrets (A9).
- **Medium.** Limited disclosure or integrity impact, or a hardening failure of an invariant that needs another flaw to matter: exposure of non-sensitive metadata to an unauthorised caller (installation ids, names of repositories the caller cannot access), a bypass of a bound that allows resource exhaustion of one process (A9), open redirect after sign-in, a missing security header, a sanitizer allowlist wider than documented but not yet exploitable, a reflected error leaking internal paths.
- **Low.** Defence in depth with no demonstrated path: verbose error text, cookie attribute inconsistencies on non-default setups, timing differences that do not expose a secret, a dependency with an advisory that the code does not reach.
- **Info.** Observations, deviations from a documented invariant without security impact, hardening ideas, and anything already listed in section 5.

**Anti-inflation rules.** A finding is not Critical or High when:

- it needs the trust ceiling (the operator, 2.7) to reach it: reading the database, the environment or the logs, editing the allowlist, replacing the image;
- it needs a capability the named attacker lacks: forging a GitHub signature without the secret, using a session the attacker does not hold, reading memory of the process, or owning a GitHub App;
- it depends on a developer flag, a test-only override (such as the variables that point the server at a fake GitHub), a mock, a fixture or a test helper;
- it needs a non-default, operator-introduced weakness (plain HTTP in production, a trivially guessable secret, a publicly exposed data volume);
- it describes an accepted residual from section 5 without a new way to exploit it;
- it affects only the attacker's own data or own session.

A chain is rated by its final outcome, but every link must itself be reachable by the named attacker.

**Worked examples.**

- A request to a board route with another user's board id returns that board: **High** (A5, attacker 2.3).
- `GET /api/issues` returns issues of a repository the session user has no access row for: **High**, or **Critical** if the repository is private and reachable without a session (A4).
- An issue comment containing a script tag or an `onerror` attribute survives the sanitizer and executes in a viewer's browser: **High** (A8, attacker 2.5).
- A webhook with an invalid signature is parsed and enqueues a refetch before rejection: **High** if it changes stored data, **Medium** if it only causes work (A9, attacker 2.4).
- The setup routes still answer after credentials are stored: **High**, **Critical** if a new App can be registered without the setup token (A7, attacker 2.1).
- A refresh token appears in an info-level log line: **High** (A3), even though only someone with log access sees it, because logs are often shipped to third parties.
- The operator can read tokens from the database with the secret: **not a finding** (2.7).
- The server accepts a `CROSSBOARD_GITHUB_API_URL` that points elsewhere: **not a finding**; it is a test-only override set by the operator.
- A missing `Secure` flag on the session cookie when served from `http://localhost`: **not a finding** (R7).
- The redirect after sign-in accepts `//evil.example` as a relative path: **Medium** (open redirect, attacker 2.1).

## 7. Disclosure split

Where a confirmed finding goes depends on its severity and on whether the repository is public.

- **Critical and High while the repository is private.** The repository is private, so its issues are not public and GitHub offers no private security advisories for it. File the finding as an ordinary tracked item labelled `security`, described neutrally (what the code does and which invariant it breaks, without exploit steps), and fix it through that item, as `.claude/rules/mdg-security.md` prescribes. Never open a public advisory or a public discussion for it.
- **Critical and High from going public.** From the point the repository is made public (with the v0.1.0 release, decision D-5), a Critical or High finding becomes a draft private security advisory on the repository, proposed first with the advisory script's `--dry-run`, fixed through the advisory's private workflow, and published only after the fix has shipped. The route is read live from the repository's visibility at the time of filing; it is never an issue on a public repository.
- **Medium, Low and Info.** Ordinary tracked items in either phase, in the normal backlog. Info findings that restate section 5 are closed with a pointer to the residual.
- **Commit messages and item text stay neutral** in both phases: they state what the code now does, with no reproduction, payload, trace or attacker narrative, and no secrets or token-shaped example strings.
- **Dependency advisories** are fixed by a version bump through the tracked dependabot flow and are never dismissed.
- **Outside reports.** While the repository is private no outside reports are expected; anyone who finds a defect tells the maintainer directly, and the maintainer files it as above. Once public, outside reporters are asked to use GitHub's private vulnerability reporting for the repository (the advisory flow above) and not to open public issues; a security policy file stating this is added to the repository when it goes public. A report received any other way is moved into the same private path before anything is written publicly.
- **Escalation.** A failed lookup of the filing route is a stop: ask the maintainer instead of guessing.
